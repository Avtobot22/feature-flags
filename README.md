# Feature Flags SDK

Feature Flags SDK - клиентская библиотека для управления доступностью функций в приложениях на Kotlin и Android через конфигурацию. Она загружает флаги, проверяет ответ и предоставляет коду приложения типизированные значения. Например, новый экран можно включить для части пользователей, а затем расширить аудиторию без новой сборки приложения.

Ядро работает на JVM без зависимости от Android. Для HTTP-загрузки, Android assets и дискового кэша есть отдельные адаптеры. Опубликованных артефактов пока нет: библиотека [подключается из исходников](docs/getting-started.md).

## Что такое фича-флаги

Фича-флаг - это именованная настройка, по которой приложение выбирает поведение. Например, флаг `feed.redesign` определяет, показывать ли новую ленту. В коде приложение проверяет его значение и открывает нужный экран. Серверная конфигурация задаёт, включён ли флаг, а приложение содержит значение по умолчанию на случай отсутствия настройки.

Это позволяет разделить выпуск кода и включение функции. Обе версии ленты уже входят в установленное приложение, но новая становится доступна после изменения конфигурации. Сам флаг не добавляет код: для функции, которой ещё нет в приложении, по-прежнему нужен релиз.

Кроме переключателя `true`/`false`, флаг может содержать параметры. Например, вместе с включением новой ленты можно передать размер страницы или текст заголовка. SDK преобразует эти параметры в тип Kotlin, который определяет приложение.

## Зачем нужен SDK

- Постепенно выпускать функцию. Сначала открыть её небольшой доле аудитории, затем увеличить процент. При неизменных ключе пользователя и группе распределение остаётся стабильным.
- Выключать проблемную функцию через конфигурацию. Приложение вернётся к предусмотренному в коде поведению после получения обновления; скорость реакции зависит от того, когда оно загружает флаги.
- Менять настройки уже реализованной функции без пересборки: например, количество элементов на странице или подпись кнопки.
- Одинаково читать флаги в разных частях приложения. Определения задают тип и дефолты, а потребители получают готовые значения через общий интерфейс чтения.

Библиотека берёт на себя чтение и проверку конфигурации, хранение активного набора, уведомления об изменениях и оценку процентных правил. Приложение определяет, где хранится серверная конфигурация, кто её меняет и когда клиент получает обновления. Доступ к защищённым операциям по-прежнему проверяет серверная авторизация.

## Как работает система

1. Приложение объявляет определения флагов: серверный ключ, тип результата и дефолты. Для параметров оно задаёт собственный decoder.
2. Приложение создаёт `FeatureFlagsSystem`, выбирает источник JSON и политику загрузки. Можно подключить локальный файл из Android assets и постоянный кэш.
3. При вызове `manager.refresh()` SDK загружает и проверяет весь документ. Только валидная конфигурация целиком заменяет активный снимок в памяти.
4. Код приложения читает значения через `reader.get()` или наблюдает за ними через `reader.observe()`. Чтение не обращается к сети или диску. Процентное правило учитывает стабильный ключ, который передаёт приложение.

До первой успешной загрузки и для отсутствующих флагов действуют дефолты из определений. Ошибка обновления сохраняет прежнюю конфигурацию. Кэш позволяет восстановить сохранённый документ после перезапуска и, при выбранной политике, использовать его при сетевой ошибке.

Приложение само запускает обновления: создание системы и подписка на изменения не делают запросов. Поэтому изменение флага на сервере становится видимым после загрузки новой конфигурации. Правила fallback, восстановления и допустимого возраста кэша описаны в [руководстве по загрузке](docs/loading-and-observation.md) и [руководстве по кэшу](docs/cache.md).

| Модуль | Назначение |
|---|---|
| `feature-flags-core` | Определения, чтение и наблюдение, загрузка, политики fallback и кэша, процентная раскатка |

## Первый пример

После [подключения `core` и `json`](docs/getting-started.md) этот JVM-пример можно запустить с `main()`. Для наглядности источник возвращает JSON из строки; в приложении его можно заменить [Retrofit-источником](docs/android-integration.md).

```kotlin
import io.github.avtobot22.featureflags.FallbackPolicy
import io.github.avtobot22.featureflags.Feature
import io.github.avtobot22.featureflags.FeatureFlagsSource
import io.github.avtobot22.featureflags.FeatureFlagsSystem
import io.github.avtobot22.featureflags.RefreshResult
import io.github.avtobot22.featureflags.json.JsonConfigurationCodec
import kotlinx.coroutines.runBlocking

fun main() = runBlocking {
    val guestMode = Feature.boolean("dashboard.guestMode", default = false)
    val system = FeatureFlagsSystem(
        remote = FeatureFlagsSource {
            """{"featureToggles":[{"feature":"dashboard.guestMode","enabled":true}]}"""
        },
        codec = JsonConfigurationCodec,
        fallback = FallbackPolicy.Never,
    )

    println(system.reader.get(guestMode)) // false: используется default

    when (system.manager.refresh()) {
        is RefreshResult.Applied -> println(system.reader.get(guestMode)) // true
        is RefreshResult.Failure -> println("Конфигурация не обновлена")
    }
}
```

`runBlocking` в этом примере предназначен для JVM. На Android запускай обновление из coroutine scope приложения или другого владельца жизненного цикла: [пример интеграции](docs/android-integration.md).

## Сборка и проверки

Нужны JDK 21, Android SDK Platform 36 и Build Tools 36.0.0. Путь к Android SDK задаётся через `ANDROID_HOME` или `sdk.dir` в локальном `local.properties`. Версии зависимостей закреплены в [version catalog](gradle/libs.versions.toml).

```sh
./gradlew qualityCheck :buildSrc:validatePlugins
python3 scripts/check_repository.py
actionlint
```

`qualityCheck` запускает статический анализ, JVM-тесты, Android lint и сборку библиотек и тестового APK. Отчёты находятся в `build/reports/` корня и модулей. Скрипт проверки файлов читает пути из индекса Git; новые файлы сначала добавь в индекс. Для workflow нужен [actionlint](https://github.com/rhysd/actionlint). В Windows используй `gradlew.bat`.

На подключённом Android-устройстве или эмуляторе:

```sh
./gradlew :feature-flags-android:connectedDebugAndroidTest
```

CI выполняет эти проверки, включая instrumented tests на эмуляторе. Изменения принимаются через PR в `main`, с объединением через squash. Сообщения коммитов и заголовок PR - на английском в формате Conventional Commits, например `docs(sdk): add usage guides`.
